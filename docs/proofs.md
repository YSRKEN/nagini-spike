# 仕様の書き方と、検証で確かめていること

[READMEに戻る](../README.md)。Pythonの確認範囲は[機能の記録](language.md)、
検査の実行手順は[環境](environments.md)を参照してください。

## 実行テストと静的検証は、確かめる範囲が違う

実行テストはコードを具体的な入力で動かして、期待した結果と比較します。
この実験のpytestは、選んだ整数について絶対値が組み込みの`abs`と一致することを調べます。

Naginiはコードを解析して、対応するPythonのモデル上で条件が常に成り立つかを調べます。
通常の`assert`も検証対象です。入力の具体例を列挙して関数を実行する方式ではありません。
ただし、pytestの中からNaginiを起動して検証結果を調べるテストもあるので、
「pytestで走らせた検査はすべて具体例の実行テスト」という区別にもなりません。

## Pythonから検証結果まで

この実験の検証は、PythonコードをNaginiがViperの中間言語へ変換し、
Viperの検証器Siliconが条件を調べ、SMTソルバーZ3を利用する流れです。
SMTソルバーは、条件を論理式として扱い、その条件に反する値があり得るかを調べる道具です。
[Naginiの公式説明](https://github.com/marcoeilers/nagini)と
[Viperの説明](https://viper.ethz.ch/tutorial/)も参照してください。

たとえば負数の分岐で`result = -x`とすると、`x < 0`のもとで`result >= 0`が成り立ちます。
ここを`result = x`に変えると、負数を返すため同じ条件を満たしません。
これは検証の考え方を簡略化した説明であり、実際に生成される論理式の全文ではありません。

検査スクリプトが証明するわけではありません。
[check.py](../scripts/check.py)はNaginiを起動して、終了コードと診断を確認します。
起動失敗や構文エラーを「誤実装を正しく拒否した」と数えないよう、
期待する条件の違反が報告されていることも確かめます。

## 二つの絶対値の例

| 例 | 仕様を書く場所 | 確かめていること |
|---|---|---|
| [absolute.py](../examples/absolute.py) | 関数内の二つのassert | 結果が非負で、入力かその符号を反転した値に等しい |
| [absolute_contract.py](../examples/absolute_contract.py) | 関数の先頭の返り値の契約 | 同じ性質に加えて、その保証を呼び出し側で利用できる |

関数内のassertと、呼び出し側に伝える契約は役割が異なります。
契約付きの例の実行上の制約は[Pythonの機能の記録](language.md)にまとめています。

## 仕様を先に決め、失敗から成功へ進む

`examples/absolute_contract.py`では、`Ensures`で「正常に返ったときに満たす条件」を
関数の先頭に宣言します。`ResultT(int)`は、その返り値を検証上で参照する記法です。
条件は、返り値が非負であり、入力かその符号を反転した値に等しいことです。

Naginiは通常、呼び出し側を検証するときに呼び出した関数の実装を展開せず、
その契約を使います。`caller`内のassertは、この保証が呼び出し側に届くことを調べます。
詳しくは[公式の契約説明](https://github.com/marcoeilers/nagini/wiki#general-contracts)を参照してください。

2026-10-10に次の順序を実際に試しました。

1. 契約と検査を先に書き、入力をそのまま返す未完成の実装で検査を実行する。
   `Postcondition of absolute might not hold`となり、非負条件の違反で失敗した。
2. 契約を変えずに、負数のときに符号を反転する分岐を実装する。
   関数自身と呼び出し側の検証が成功した。
3. 一時コピーで負数の分岐を壊す。同じ返り値の条件で失敗した。
4. 別の一時コピーで、非負の返り値を保証する宣言だけを外す。
   実装は正しいままでも、呼び出し側の`assert result >= 0`が検証に失敗した。

3と4は毎回の検査にも含めています。宣言の削除は検証の仕組みを調べるための実験で、
実装を完成させる際の回避策ではありません。今回、1から2の間で仕様は変えていません。
実行用コピーの抽出では現在の二つの宣言を確認しますが、
リポジトリ全体で将来の仕様変更を禁止する仕組みまでは導入していません。

## 検証した実装を、契約の除去後に実行する

[extract_absolute.py](../scripts/extract_absolute.py)は、既知の二つの契約宣言と
専用importの行だけを除去します。計算部分を別の実装で書き直す方式ではありません。
元のコードがNaginiの検証に成功した後で、実行用コピーを保存します。

[抽出のテスト](../tests/test_extract_absolute.py)では、生成したコピーを別プロセスで実行し、
絶対値の結果と呼び出し側を具体例で確認しています。
抽出処理自体の検査として、誤実装を渡したときに勝手に修正しないことと、
呼び出し側のassertが残り、負数の誤った返り値を実行時に拒否することも確認しました。
この誤実装の抽出テストは、検証後に保存する通常の生成手順とは分けています。

抽出は自作の処理であり、その一般的な正しさをNaginiで証明したわけではありません。
今回の構成以外の契約付きコードを扱えるとは結論付けていません。
静的検証は元のファイルに対する結果で、抽出後のコピーは実行テストでも確かめる、という境界です。

## whileループで範囲の和を検証する

[sum_range.py](../examples/sum_range.py)では、非負の整数nについて0からn未満までを足します。
固定した仕様は、最後の`assert 2 * total == n * (n - 1)`です。
これは`total = n * (n - 1) / 2`という範囲の和を、除算なしで表した条件です。
この例でPythonの除算を検証したわけではありません。

最初は`total = 0`だけの未完成の実装で検査を実行し、nが2以上の実行例と
Naginiの静的検証が失敗しました。仕様を変えずにwhileループを実装し、
ループ先頭に次の二つの不変条件を加えると検証が成功しました。

| 不変条件 | 意味 |
|---|---|
| `0 <= i and i <= n` | 次に足す数iが、範囲の中にある |
| `2 * total == i * (i - 1)` | totalが0からi未満までの和である |

ループ不変条件は、ループに入る前に成立し、一周しても保たれる条件です。
開始時はiとtotalがともに0なので成立します。
一周でiを足し、iを1増やすと、次のiについて同じ関係が保たれます。
終了時は`i >= n`と範囲の不変条件から`i == n`が分かり、途中の和の条件から最後の仕様が導けます。
Naginiでの記法は[公式の説明](https://github.com/marcoeilers/nagini/wiki#loop-invariants)も参照してください。

2026-10-10に、[テスト](../tests/test_sum_range.py)で次の結果を確認しました。

| 検査 | 結果 |
|---|---|
| 正しい実装と二つの不変条件 | Naginiの検証成功。0・1・2・5・10・100の実行結果も`sum(range(n))`と一致 |
| `total += i`を`total += i + 1`に変更 | `Loop invariant might not be preserved`で失敗。通常実行でも最後のassertが失敗 |
| 和の不変条件だけを削除 | 最後の和のassertを証明できず失敗。ただし通常実行のn=10では正しい45を返した |
| 負数を入力 | 通常実行の入力チェックが`AssertionError`で拒否 |

不変条件を外した版の失敗は、実装の誤りを発見したという意味ではありません。
正しい計算でも、検証に必要な情報が足りないと証明できないことを示す実験です。
二つの変更コピーでも最後の仕様は維持しています。
Naginiの検証対象の入力は`Requires(n >= 0)`で限定し、具体例の実行だけで一般化していません。

この実験で確認したのは、ループ後の和の正しさです。
停止性を別の契約で形式的に検証したわけではなく、for・break・continueや、ループ内で可変コレクションを扱うことは未確認です。

## 整数リストの先頭を読む

[list_head.py](../examples/list_head.py)の仕様は、空リストなら0、
要素があるなら先頭の値を返すことです。最後の二つの通常のassertで表しています。
先にこの仕様と検査を書き、0を返すだけの未完成の実装が失敗することを確認しました。
その後、仕様を変えずに空の場合を分岐し、非空の場合に添字0を読んで成功しました。

リストは内容や長さが変わり得るので、Naginiの証明モデルでは読み取りの権限が必要です。
この例は`Requires(Acc(list_pred(values), 1 / 2))`を前提として宣言しています。
`list_pred`はリストに関する権限を表す組み込みの記法で、
`Acc`の分数はデータの何割を読むかではなく、読み取り専用の権限を表します。
公式の説明は[権限の仕様](https://github.com/marcoeilers/nagini/wiki#permission-assertions)を参照してください。

2026-10-10に、[テスト](../tests/test_list_head.py)で次の結果を確認しました。

| 検査 | Naginiの結果 | 通常のPythonの具体例 |
|---|---|---|
| 正しい実装と読み取り専用の権限 | 成功 | 空・単一・複数要素、負数、大きな整数で結果が一致し、入力も不変 |
| `values[0]`の代わりに`values[1]`を読む | 添字1を読む条件で失敗 | 要素が一つのリストで`IndexError` |
| 権限の宣言だけを外す | 長さを読む条件で権限不足を報告 | `[7]`では正しく7を返した |
| 同じ権限のまま`values[0] = 0`を加える | 書き込みの条件で権限不足を報告 | 実行時には書き込みを阻止しない。期待する返り値と入力の検査が失敗 |

三つの変更コピーでも最後の仕様は維持しています。
宣言の削除による失敗は、Pythonの計算にバグがあるという意味ではありません。
書き込みの拒否も、Pythonが実行時にデータを保護するという意味ではなく、
読み取り専用の前提からは書き込めないことを静的検証で調べた結果です。

この例で確認したのは、整数リストの先頭の読み取りだけです。
この読み取り実験では、リストを変更する正しい実装や、
呼び出し側への権限の返却を宣言する契約は対象外です。
別名参照、並行実行、リスト全体を走査するループにも結果を一般化していません。

## 整数リストの先頭を書き換える

[list_write.py](../examples/list_write.py)は、要素があれば先頭を指定値に置き換え、
空なら何もしません。まず最後の二つのassertと実行テストを書き、
何もしない未完成の実装が失敗することを確認しました。
その仕様を変えずに、空の場合を分けて添字0に代入すると検証が成功しました。

静的仕様は`len(values) == length`と、`len(values) == 0 or values[0] == value`です。
`length`は書き換える前に読み取った長さです。
入力が空なら長さが0のまま、非空なら先頭が指定値になることを確認しています。

前提の`Requires(Acc(list_pred(values)))`では権限の分数を省略しています。
Naginiでは省略時は完全な権限で、読み取りに加えて書き込みもできます。
これはPythonの実行時のアクセス制御ではなく、静的検証のモデル上の条件です。
詳しくは[公式の権限説明](https://github.com/marcoeilers/nagini/wiki#permission-assertions)を参照してください。

2026-10-10に、[テスト](../tests/test_list_write.py)で次の結果を確認しました。

| 検査 | Naginiの結果 | 通常のPythonの具体例 |
|---|---|---|
| 正しい実装と書き込み可能な権限 | 成功 | 空・単一・複数要素、負数、大きな整数で期待したリストと一致 |
| 指定値の代わりに`value + 1`を代入 | 先頭の値のassertで失敗 | 同じassertが失敗 |
| 権限を`1 / 2`の読み取り専用に変更 | 代入の条件で権限不足を報告 | 通常実行では正しく書き換えられた |
| 二つ目の要素も0に変更 | 成功 | `[7, 99]`に9を指定した例で、期待した`[9, 99]`と一致せず検査が失敗 |

最後のコピーがNaginiで通るのは、現在の静的仕様が先頭以外の値を制限していないためです。
長さと先頭の値については、余分な変更を含むコピーも条件を満たしています。
検証器の誤りを示したわけではなく、仕様の十分さと検証成功を分けるための実験です。
変更コピーでも最後の二つのassertは維持しています。

正しい実装が先頭以外を変更しないことは、今回の実行テストで確認しています。
その性質をすべての入力について静的仕様で保証することや、
呼び出し側に変更結果と権限を返す契約の検証は今回の対象外です。
この結果を、リスト全体の変更や別名参照・並行実行に一般化していません。

## 変更範囲を仕様で縛る

前節の例では、先頭以外の値を静的仕様に含めていませんでした。
[list_frame.py](../examples/list_frame.py)では、同じ書き換え処理に次の条件を加えます。

```python
before = ToSeq(values)
# この後で先頭を書き換える。
Assert(Forall(int, lambda i: Implies(1 <= i and i < len(values), values[i] == before[i])))
```

`before`は検証上の変更前の内容です。`Forall`は「すべての整数iについて」、
`Implies`は「iが1以上で長さ未満なら」という条件の適用範囲を表します。
つまり、先頭を除いたすべての要素の値が元のままであることを求めています。
既存の長さと先頭の値のassertも維持しています。

2026-10-10に[テスト](../tests/test_list_frame.py)で確認しました。
まず余分な書き換えを拒否するテストを作り、弱い仕様のままでは検証成功のためテストが失敗しました。
次に条件を追加すると、同じ書き換え処理は検証に成功し、
二つ目の要素を0にするコピーはこの`Forall`の条件で拒否されました。
拒否テストでは終了コードに加え、この条件を名指しした診断を確認しています。

空・単一・複数要素の通常実行も期待値と一致しました。
ただし、この追加条件は静的検証専用です。配布物のスタブは通常実行では条件を検査せず、
lambda内の比較も実行されません。具体例の確認は別のpytestのassertで行っています。

今回の保証は、関数内部で最後の条件が成立することです。
呼び出し側が利用できる事後条件や権限の返却、別名参照・並行実行の検証は含めていません。
仕様を強めた結果と、前節の弱い仕様が通る結果を区別して残しています。

## リストの結果と権限を呼び出し側へ返す

[list_contract.py](../examples/list_contract.py)は、非空のリストの先頭を書き換えます。
関数内部の最後のassertだけでなく、呼び出し側が利用できる保証を`Ensures`で宣言します。
入力側の前提は書き込み権限と非空であること、出力側の保証は次の三つです。

```python
Ensures(Acc(list_pred(values)))
Ensures(len(values) == Old(len(values)))
Ensures(values[0] == value)
```

一つ目は関数に渡した権限を呼び出し側へ返すこと、二つ目は長さの維持、
三つ目は指定した先頭の値です。権限は検証モデル上の読み書きの条件であり、
PythonやOSのアクセス制御ではありません。
呼び出し側は長さと値をassertで確認した後、先頭をさらに`value + 1`に変更します。

2026-10-10に[テスト](../tests/test_list_contract.py)で確認しました。
三つの事後条件と呼び出し側の検査を先に固定し、何もしない実装は先頭の事後条件で失敗しました。
その契約を変えずに代入を実装すると、関数と呼び出し側の検証が成功しました。

| 変更 | 実際の拒否箇所 |
|---|---|
| 実装で指定値より1大きい値を代入 | 関数の先頭の値の事後条件 |
| 返す権限を読み取り専用の`1 / 2`に弱める | 呼び出し後の`values[0] = value + 1`で権限不足 |
| 先頭の値の事後条件だけを省く | 呼び出し側の`assert values[0] == value` |

最後の例は実装を変えていません。それでも呼び出し側では保証を使えなくなります。
関数の中身が正しいことと、契約が呼び出し側に必要な情報を渡すことを区別する実験です。

通常のPythonによる直接実行は、配布物の`Ensures`で例外になりました。
実行確認は、検証に成功したソースから既知の三つの事後条件だけを除いたコピーで行います。
ソースの同一性と宣言の出現回数を確認し、単一・複数要素や大きな整数で、
関数の変更と呼び出し後の再変更が期待値と一致しました。
この除去処理はテスト内に限定しており、一般のプログラムへの抽出の正しさを保証しません。

この契約は非空リストに限り、先頭以外の値の維持を呼び出し側へ保証する条件はありません。
前節の全要素の条件との組み合わせ、別名参照や並行実行は検証していません。

## リストの走査と途中の条件

[list_scan.py](../examples/list_scan.py)は、非負整数のリストの合計を返します。
この実験の静的仕様は、入力の各要素が0以上なら最後の結果も0以上になることです。
正確な合計値については、別の実行テストで具体例を確認します。

前提として読み取り専用の権限と全要素の非負性を与え、ループ内には次の条件を置きます。

```python
Invariant(Acc(list_pred(values), 1 / 2))
Invariant(Forall(values, lambda value: value >= 0))
Invariant(0 <= i and i <= len(values))
Invariant(total >= 0)
```

最初は、仕様とテストを固定し、合計の初期値を-1にした未完成の実装で失敗を確認しました。
実行テストでは合計が合わず、Naginiではループに入る時点の`total >= 0`が成立しません。
初期値を0にすると、同じ仕様とループの検証が成功しました。

2026-10-10に[テスト](../tests/test_list_scan.py)で次の比較を確認しました。

| コピーの変更 | Naginiの結果 | 通常のPythonで`[1, 2, 3]`を与える |
|---|---|---|
| 正しい足し算 | 成功 | 6と一致 |
| 足し算を引き算に変更 | `total >= 0`の不変条件を維持できず拒否 | 最後のassertで失敗 |
| 権限の不変条件だけを除く | 残った全要素の条件内のリストの前提で権限不足 | 計算は変更していないので6と一致 |
| 足し算自体を省く | 成功 | 0になり、期待値6との比較で失敗 |

入力の読み取り権限を関数入口に書くだけでは、ループの証明で使う情報が足りませんでした。
一方、最後のコピーは権限も非負性も維持しますが、和を計算していません。
検証が成功することと、仕様が目的の計算を十分に縛ることを区別しています。

通常実行では、空・単一・複数要素、0、大きな整数を選び、組み込みの`sum`と入力の不変性を確認しました。
負の要素の例は、ループ内の通常のassertで拒否されました。
静的検証の入力の前提を、`Requires`が実行時に強制するわけではありません。
正確な合計値の静的保証、停止性、呼び出し側の契約、負数も含む一般の和は検証していません。

## 辞書のキー存在と読み取り権限

[dict_read.py](../examples/dict_read.py)は、整数の辞書から指定したキーの値を返し、
キーが存在しないときは0を返します。最後の二つのassertを仕様として先に固定しました。

```python
assert key in values or result == 0
assert key not in values or result == values[key]
```

一つ目は不在時の0、二つ目は存在時の対応する値を求めます。
Pythonの`or`は左側が真なら右側を評価しないので、キーが不在のときに二つ目の添字参照は実行されません。
この参照の安全性もNaginiで検証しました。

最初は、キーがあっても0を返す未完成の実装で実行テストと証明が失敗しました。
同じ仕様のまま存在するキーの値を読み取ると、検証に成功しました。
読み取り用の前提には`Acc(dict_pred(values), 1 / 2)`を指定しています。
権限はNaginiのモデル上の条件であり、PythonやOSのアクセス制御ではありません。

2026-10-10に[テスト](../tests/test_dict_read.py)で比較しました。

| コピーの変更 | Naginiの結果 | 通常のPythonで`{1: 7}`、キー1を与える |
|---|---|---|
| 正しい実装 | 成功 | 7を返し、入力も維持 |
| 存在を調べたキーの代わりに`key + 1`を読む | その添字の前提で拒否 | キー2が存在せず`KeyError` |
| 読み取り権限の前提を除く | `key in values`の前提で権限不足 | 計算は同じなので7を返す |
| 読み取り権限で`values[key] = 0`を加える | 代入の前提で権限不足 | 辞書を書き換え、外側の期待値のassertが失敗 |

拒否のテストは終了コードと検証失敗の診断に加え、該当する操作や権限不足の理由を確認します。
起動や変換の失敗を、誤実装の拒否として扱いません。
通常実行では、空・キーの有無・ゼロ・負数・大きな整数の具体例を組み込みの`dict.get`と照合しました。
`dict.get`自体をNaginiで検証した結果ではありません。
この結果を、辞書の書き込み・削除・走査、文字列キー、呼び出し側の契約や並行実行へ一般化していません。

## Bend 2の実験から取り入れた役割分担

[bend2-spikeの説明](https://github.com/YSRKEN/bend2-spike/blob/main/docs/proofs.md)では、
実装、法則、証明を別々のファイルに置いています。
このリポジトリでは、同じファイル構成をそのまま再現してはいません。

| 役割 | 現在のNaginiの例 |
|---|---|
| 実装 | 関数の分岐と返り値 |
| 仕様 | assert、または`Ensures`で宣言する返り値の条件 |
| 検証 | Naginiが自動で条件を調べ、テストがその成功・失敗を確認する |

Naginiで独立した証明ファイルが必要なことを確認したわけではありません。
現在は実装と契約を同じPythonファイルに置き、実装を直す際は契約を維持しています。
条件を固定したまま誤実装を拒否することと、保証の範囲を記録する方針を取り入れています。

## 何を信頼し、何は未確認か

この実験はNaginiの健全性を証明するものではありません。
PythonからViperへの変換、Viper、Z3、PythonとJavaの処理系を信頼しています。
Leanの小さなカーネルで独立した証明を再検査する手順は、この構成にはありません。

Naginiで扱える範囲は、対応するPythonの処理をViper上に表現できる範囲に限られます。
変換できないことと、変換できても条件を証明できないことは区別します。
検証の失敗だけで必ず実装にバグがあるとは言えず、注釈や契約が不足する場合もあります。
今回の故意の誤実装では、狙った非負条件の違反を確認しています。

assertの削除、成立しない前提による検証逃れ、外部ライブラリの契約と実装の一致は未確認です。
契約の一部を外す実験は行いましたが、あらゆる仕様の弱体化を検出する検査ではありません。
現在の成功を、任意のPythonプログラムや外部ライブラリの正しさに一般化はできません。
