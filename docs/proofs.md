# 仕様の書き方と、検証で確かめていること

[READMEに戻る](../README.md)。Pythonの確認範囲は[機能の記録](language.md)、
検査の実行手順は[環境](environments.md)を参照してください。

## 実行テストと静的検証は、確かめる範囲が違う

実行テストはコードを具体的な入力で動かして、期待した結果と比較します。
この実験のpytestは、選んだ整数について絶対値が組み込みの`abs`と一致することを調べます。

Naginiはコードを解析して、対応するPythonのモデル上で条件が常に成り立つかを調べます。
通常の`assert`も検証対象です。入力の具体例を列挙して関数を実行する方式ではありません。
ただし、pytestの中からNaginiを起動して検証結果を調べるテストもあるので、
「pytestで走らせた検査はすべて具体例の実行テスト」という区別にもなりません。

## Pythonから検証結果まで

この実験の検証は、PythonコードをNaginiがViperの中間言語へ変換し、
Viperの検証器Siliconが条件を調べ、SMTソルバーZ3を利用する流れです。
SMTソルバーは、条件を論理式として扱い、その条件に反する値があり得るかを調べる道具です。
[Naginiの公式説明](https://github.com/marcoeilers/nagini)と
[Viperの説明](https://viper.ethz.ch/tutorial/)も参照してください。

たとえば負数の分岐で`result = -x`とすると、`x < 0`のもとで`result >= 0`が成り立ちます。
ここを`result = x`に変えると、負数を返すため同じ条件を満たしません。
これは検証の考え方を簡略化した説明であり、実際に生成される論理式の全文ではありません。

検査スクリプトが証明するわけではありません。
[check.py](../scripts/check.py)はNaginiを起動して、終了コードと診断を確認します。
起動失敗や構文エラーを「誤実装を正しく拒否した」と数えないよう、
期待する条件の違反が報告されていることも確かめます。

## 二つの絶対値の例

| 例 | 仕様を書く場所 | 確かめていること |
|---|---|---|
| [absolute.py](../examples/absolute.py) | 関数内の二つのassert | 結果が非負で、入力かその符号を反転した値に等しい |
| [absolute_contract.py](../examples/absolute_contract.py) | 関数の先頭の返り値の契約 | 同じ性質に加えて、その保証を呼び出し側で利用できる |

関数内のassertと、呼び出し側に伝える契約は役割が異なります。
契約付きの例の実行上の制約は[Pythonの機能の記録](language.md)にまとめています。

## 仕様を先に決め、失敗から成功へ進む

`examples/absolute_contract.py`では、`Ensures`で「正常に返ったときに満たす条件」を
関数の先頭に宣言します。`ResultT(int)`は、その返り値を検証上で参照する記法です。
条件は、返り値が非負であり、入力かその符号を反転した値に等しいことです。

Naginiは通常、呼び出し側を検証するときに呼び出した関数の実装を展開せず、
その契約を使います。`caller`内のassertは、この保証が呼び出し側に届くことを調べます。
詳しくは[公式の契約説明](https://github.com/marcoeilers/nagini/wiki#general-contracts)を参照してください。

2026-10-10に次の順序を実際に試しました。

1. 契約と検査を先に書き、入力をそのまま返す未完成の実装で検査を実行する。
   `Postcondition of absolute might not hold`となり、非負条件の違反で失敗した。
2. 契約を変えずに、負数のときに符号を反転する分岐を実装する。
   関数自身と呼び出し側の検証が成功した。
3. 一時コピーで負数の分岐を壊す。同じ返り値の条件で失敗した。
4. 別の一時コピーで、非負の返り値を保証する宣言だけを外す。
   実装は正しいままでも、呼び出し側の`assert result >= 0`が検証に失敗した。

3と4は毎回の検査にも含めています。宣言の削除は検証の仕組みを調べるための実験で、
実装を完成させる際の回避策ではありません。今回、1から2の間で仕様は変えていませんが、
実行用コピーの抽出では現在の二つの宣言を確認しますが、
リポジトリ全体で将来の仕様変更を禁止する仕組みまでは導入していません。

## 検証した実装を、契約の除去後に実行する

[extract_absolute.py](../scripts/extract_absolute.py)は、既知の二つの契約宣言と
専用importの行だけを除去します。計算部分を別の実装で書き直す方式ではありません。
元のコードがNaginiの検証に成功した後で、実行用コピーを保存します。

[抽出のテスト](../tests/test_extract_absolute.py)では、生成したコピーを別プロセスで実行し、
絶対値の結果と呼び出し側を具体例で確認しています。
抽出処理自体の検査として、誤実装を渡したときに勝手に修正しないことと、
呼び出し側のassertが残り、負数の誤った返り値を実行時に拒否することも確認しました。
この誤実装の抽出テストは、検証後に保存する通常の生成手順とは分けています。

抽出は自作の処理であり、その一般的な正しさをNaginiで証明したわけではありません。
今回の構成以外の契約付きコードを扱えるとは結論付けていません。
静的検証は元のファイルに対する結果で、抽出後のコピーは実行テストでも確かめる、という境界です。

## Bend 2の実験から取り入れた役割分担

[bend2-spikeの説明](https://github.com/YSRKEN/bend2-spike/blob/main/docs/proofs.md)では、
実装、法則、証明を別々のファイルに置いています。
このリポジトリでは、同じファイル構成をそのまま再現してはいません。

| 役割 | 現在のNaginiの例 |
|---|---|
| 実装 | 関数の分岐と返り値 |
| 仕様 | assert、または`Ensures`で宣言する返り値の条件 |
| 検証 | Naginiが自動で条件を調べ、テストがその成功・失敗を確認する |

Naginiで独立した証明ファイルが必要なことを確認したわけではありません。
現在は実装と契約を同じPythonファイルに置き、実装を直す際は契約を維持しています。
条件を固定したまま誤実装を拒否することと、保証の範囲を記録する方針を取り入れています。

## 何を信頼し、何は未確認か

この実験はNaginiの健全性を証明するものではありません。
PythonからViperへの変換、Viper、Z3、PythonとJavaの処理系を信頼しています。
Leanの小さなカーネルで独立した証明を再検査する手順は、この構成にはありません。

Naginiで扱える範囲は、対応するPythonの処理をViper上に表現できる範囲に限られます。
変換できないことと、変換できても条件を証明できないことは区別します。
検証の失敗だけで必ず実装にバグがあるとは言えず、注釈や契約が不足する場合もあります。
今回の故意の誤実装では、狙った非負条件の違反を確認しています。

assertの削除、成立しない前提による検証逃れ、外部ライブラリの契約と実装の一致は未確認です。
契約の一部を外す実験は行いましたが、あらゆる仕様の弱体化を検出する検査ではありません。
現在の成功を、任意のPythonプログラムや外部ライブラリの正しさに一般化はできません。
