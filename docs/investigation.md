# 実用Python機能の調査台帳

正本は `docs/investigation.json`。次の問いは調査の候補であり、対応しているという主張ではない。初期状態は全件 `unconfirmed` とする。既存テストの成功から別の入力域や機能の対応を推定しない。

## 検査と完了

`python scripts/check_investigation.py` は型・キー・状態・証拠参照の整合性を検査する。未確認が残っても通常検査は通る。

`python scripts/check_investigation.py --require-complete --candidate-reviewed` は未確認が一件でも残れば終了コード1で拒否する。空台帳、未知状態、重複ID、証拠不足、不正な証拠パスも拒否する。このコマンドが通るまで調査全体を完了として扱わない。通常の `scripts/check.py` にも整合性検査を含める。

## 記録する契約

各問いは `id`、`question`、`status`、`scope`、`reproduction`、`expected`、`actual`、`diagnosis`、`evidence` を持つ。確認済み状態には具体的な版と入力域などの限定条件、再現コマンド、期待結果、実結果、分類の診断根拠が必要。`evidence` はリポジトリ内の空でないPython再現例と診断ログ（`.log`、`.txt`、`.json`）への相対パスを含める。個人情報やローカル環境の絶対パスを記録しない。

| 状態 | 意味 |
| --- | --- |
| unconfirmed | 実験と分類がまだ終わっていない |
| verified | 記録した限定条件の正実装が検証に成功した |
| insufficient_specification | 仕様が弱く、意図した性質を保証できない根拠がある |
| rejected_incorrect | 意図的誤実装が狙った条件の違反で拒否された |
| translation_failed | 再現例が検証器への変換段階で失敗した |
| unsupported | 対象版の未対応を具体的な診断や一次資料で特定した |

起動失敗・時間切れ・環境故障を `rejected_incorrect` にしない。問いの範囲を絞れない、または分類が未解決なら `unconfirmed` のままにする。

この機構はファイルの存在、非空、パス境界と記録の契約を検査する。記録された主張の真偽、コマンドが本当に実行されたこと、ログと版の一致はファイルの存在だけでは証明できない。再現実行と診断内容の照合を別途行う必要がある。ゲート自身の合成テストはPython機能の調査証拠ではない。

## 候補

階乗の問いは非負整数全体を対象とし、Requiresを0〜4に狭めない。独立した一般階乗定義の同一Ensuresで正実装と偽多項式を比較する。

[全題材のdone・未確認一覧](progress.md)を参照してください。各行の状態はJSON台帳と一致するよう生成します。

次回の狭い追加未確認項目として、`factorial-loop-model` を台帳に登録した。
問いは「独立Pure再帰モデルと一致するwhile実装を、Assume/Trustedなしで証明できるか」。
初回の不変条件保存と再帰式Assertは証明未達、Pure再帰Ensuresは診断変換例外だった。
これを未対応の確定とはせず、次回に証明情報の与え方を再探索する。
再帰正実装とHorner偽多項式の比較が成功した `factorial-general` とは区別する。
`list-append` は任意長・全権限の範囲で確認済み。長さ1増・全旧要素保存・新末尾一致と権限返却を同一Ensuresで証明し、三つの独立誤例を各事後条件で拒否した。その他の未確認項目は残す。

## 完了検査の実行前ガード

完了候補として証拠と未解決範囲を照合した後だけ、`--require-complete --candidate-reviewed` を同時に指定する。片方だけなら終了コード2で拒否し、台帳検査本体を呼ばない。通常の整合性検査は従来どおりである。

`--candidate-reviewed` はレビューを行ったという明示であり、その内容の十分性を機械で保証するものではない。両方を指定しても未確認・証拠不足の拒否は維持する。未確認がある段階でのガード検査には実台帳を使わず、合成検査と専用テストを使う。Python最適化モードでも入口の拒否を確認する。

## Optional整数のNone分岐

`optional-narrow` は制限のない `Optional[int]` に対する一般契約で確認した。Noneなら0、整数なら入力+1を二つの短絡or事後条件で指定し、前提追加なしでNone分岐後の加算を証明した。None側だけ1を返す誤例と整数側だけ入力を返す誤例を、同じ契約の対応する事後条件で個別に拒否した。

実在する契約付きstub(return0)と成功期待テストを先に固定し、実Naginiが整数側事後条件を拒否する赤を確認した。対象3テストは36.90秒。具体例7件の通常実行は一般静的証明とは別証拠である。Optional戻り値の検索条件やリスト・ループとの組合せは未確認のまま残す。全体完了とは扱わず、実台帳の完了ゲートは実行しない。

最終の `scripts/check.py` は終了コード0。通常台帳整合性・lint・38ファイル整形・strict型検査、全pytest（172件、600.56秒）、最後のNagini正例成功と狙ったAssert誤例拒否がすべて成功した。保存証拠は `docs/evidence/optional-final-check.log`。全体の台帳はverified 3件・unconfirmed 23件であり、完了候補検査は実行していない。

## 進捗表の更新

`docs/investigation.json`を更新したら、リポジトリのルートで`python scripts/render_progress.py`を実行し、生成された`docs/progress.md`も同じ変更に含めます。既存の仮想環境なら`.venv\Scripts\python.exe scripts\render_progress.py`で実行できます。

表はID・問い・状態・コードと診断へのリンクを全件表示します。doneは問いの調査と分類が済んだという意味で、証明成功・誤実装拒否・非対応・変換失敗・仕様不足を区別します。未確認には未着手と証明未達を含みます。基礎実験の一覧と実用調査の台帳は対象が異なるため、件数を混ぜません。

通常の`scripts/check.py`は`python scripts/render_progress.py --check`も呼び、台帳と表の不一致を拒否します。検査は表を書き換えません。これは表示の更新漏れの検査であり、調査内容の十分性を判定する完了検査ではありません。

## 文字列の連結内容と長さ

`string-length` は制限のない任意の二文字列 `a,b` について、`Result()==a+b` と `len(Result())==len(a)+len(b)` を同じ一般契約に指定し、正実装を証明した。順序交換は長さを保ちながら内容条件で拒否された。余分な文字を追加する誤例は内容と長さの両方を壊し、長さ条件で拒否された。長さだけを壊す独立誤例という意味ではない。

実在する `return a` stubと成功期待pytestを先に固定して内容事後条件の赤を取得した。初回は内容Ensuresを先に宣言しており、余分文字誤例も内容診断のみだった。二つの条件の論理内容を保って宣言順を長さ先へ調整し、長さ診断を取得した。この題材の観測であり一般的な診断順序を保証しない。初回ログと最終ログは別証拠で残す。

最終正例は12.41秒、順序交換は10.75秒で内容条件 `@22.12--22.29`、余分文字は10.97秒で長さ条件 `@21.12--21.44` を終了コード1で拒否。対象3テストは36.41秒。空文字・ASCII・日本語・絵文字を含む通常実行6例は一般静的証明とは別の有限証拠。検索・添字・I/Oや実用組合せは未確認で、調査全体は未完である。実台帳の完了検査は実行しない。
